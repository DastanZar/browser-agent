## Profile sync (`core.sync_user_profile`, `/api/profile/sync`): concerns for the owner to decide

I haven't changed this code. I started a safer redesign, but this session's environment safety check blocks
me from working on code that reads the owner's Chrome credentials. So it's described here, for the owner.

1. **It copies `Web Data`**, which holds saved credit cards and addresses, into a profile an AI agent drives,
   where autofill can offer them on pages the agent visits on its own. Suggest not copying it.
2. **It copies the whole cookie jar** (bank, email, everything) into a profile that runs with a debugging port.
   Chrome 136 blocks remote debugging on the real profile because any local program can read every cookie
   through that port. That bypasses Windows' app-bound cookie encryption. Copying everything recreates that
   exposure for every site, not just the ones the agent needs. Suggest copying only the sites the owner picks.
3. **It runs silently on the first launch** of the agent browser (`open_agent_chrome`), without the owner
   asking. Suggest making it explicit only: the button.
4. **It overwrites the agent's own `Cookies` and `Local State`.**
   - Logins made in the sign-in window are lost.
   - Anything the agent profile had encrypted with its old key can't be read any more.
   - Merging needs the cookies re-encrypted by Chrome. One way: a throwaway headless Chrome on a copy of the
     profile, `Storage.getCookies` there, then `Storage.setCookies` into the agent browser.
5. **It can copy into `~/.agent-chrome` while the agent Chrome is running.** The files are then overwritten
   under a live process. Close it first (`close_agent_chrome()`) and drop the dashboard's browser session.
6. **The profile pick order** prefers "Profile 2" before "Default", then the largest cookie file. That's a
   surprising default; the owner should be able to choose.

## Windows "desktop visibility" fix (`_spawn`)

Python's `subprocess.STARTUPINFO` has no `lpDesktop` field: CPython's `CreateProcess` wrapper only reads
`dwFlags`, `wShowWindow`, the std handles and `lpAttributeList`. Setting `si.lpDesktop` does nothing.
- It's harmless, but it doesn't change visibility.
- A child normally inherits the parent's desktop anyway.
- If the owner saw hidden windows, the cause is elsewhere. Worth a repro: does the launcher run elevated, as a
  service, or from a scheduled task?
