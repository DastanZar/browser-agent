## Changed, with reasons

1. **The default bind went from `0.0.0.0` back to `127.0.0.1`; LAN is opt-in (`DASHBOARD_HOST=0.0.0.0`).**
   - The dashboard drives the owner's logged-in browser (LinkedIn, Google, banking).
   - Listening on every interface by default exposes it on any network the laptop joins (cafés, offices).
2. **Restored the Host-header check (`allowed_hosts()` / `host_ok()`).**
   - Without it, any website can rebind its domain to 127.0.0.1.
   - The browser then treats `http://evil.example:8770/` as same-origin. `is_local_request()` sees a client of
     127.0.0.1, serves the page with the token inside, and the attacker's script reads it. That's full control
     of the agent.
   - In LAN mode the check also allows the LAN IP and the hostname, so phone access still works. More names
     can be added with `DASHBOARD_ALLOWED_HOSTS`.
3. **The cookie no longer authorises API calls; only the page load.**
   - Browsers attach cookies to requests from other sites on the same host (another local dev server on a
     different port is "same-site"). A custom `X-Token` header can't be added cross-site without a CORS
     preflight, which we don't answer.
   - The UI already sends `X-Token`, so nothing broke.
   - The cookie is now only set in LAN mode, with `samesite=strict`.
4. **The startup banner no longer prints the token in local mode.** In LAN mode it prints the link plus a
   one-line warning.
5. **The Notion config file is now `chmod 600`** (it holds the Notion token).
6. **`agent.py`: restored `--no-fast`.** Its removal turned fast mode off in the terminal. Fast mode measured
   2–4× faster with approvals intact (docs/ENGINEERING.md); the dashboard keeps its own checkbox.

All of the above is pinned by `tests/test_offline.py::test_dashboard_rejects_foreign_host_and_cookie_only_api`.

## Your turbo commit (156cbec): reviewed after a rebase

Arrived while I was merging, so I rebased onto it (no force-push).
1. **Ad blocking was a no-op.** `step_hook` called `browser.session_manager.get_current_target()` and
   `get_or_create_session()`, which don't exist in browser-use 0.13.10. The `AttributeError` was swallowed by
   `except Exception: pass`, so the blocklist never applied.
   - Fixed: it's now called as `turbo.enable_cdp_ad_blocking(browser)`; the BrowserSession has
     `get_or_create_cdp_session()`.
   - Tested in Chrome: a `…doubleclick.net…` fetch is BLOCKED, and a normal URL loads (200).
   - The blocklist only covers the focused tab, not tabs opened later (e.g. by `read_link`).
2. **Pre-navigation overlapped with my `core.start_url`.** Kept both:
   - With turbo on (the dashboard default), your `extract_target_url` is used. It also understands names like
     "open YouTube".
   - With turbo off (CLI, digests), `start_url` opens explicit URLs and domains only.
   - Every task still starts in a new tab of its own.
3. **`extract_target_url` step 4** maps any mention of a known name to that site ("summarise this page about
   GitHub" opens github.com). Low cost, since the agent can navigate back, but it fights tasks about the
   current tab. Consider limiting step 4 to tasks that don't mention "this page/tab".
4. **The prompt compiler** rewrites tasks with an LLM before dispatch. Its example blueprint includes
   "Click Connect -> Add note or Send". The gate still asks before every Connect/Send, but at LinkedIn scale
   that's the pattern its User Agreement §8.2 bans. Suggest dropping that example, and keeping the "max
   targets" guardrail.
5. **`get_turbo_timings()`** is defined but not used anywhere. Browser Use's defaults are already 0.25 s and
   0.5 s, so the gain would be small.
